# 阈值调优 · 双门槛量化依据

> 本文档回答一个问题：**「分类概率 ≥ 60% 且 处理条件概率 ≥ 60%」这两个门槛为什么是这两个数字，以及怎么在数据变化后重新校准它们。**
>
> 数据基线：**v0.3（L3 补强版）** · 230 条独立评估集（与训练集零重叠，含 22 条直播中断类）上的回放实测，
> 生成链路 `replay_eval.py → threshold_scan.py`，全部报告见 `backend/evals/reports/`。
> v0.2 基线的同套扫描结论方向一致（见 git 历史）。

## 1. 双门槛体系的职责边界

```
模型（Laya 微调 + 分桶温度校准）          程序（routing.ts 阈值分流）
────────────────────────────            ─────────────────────────────
Choice: 类别 + 全候选概率分布     ──▶    classifyProbability = 0.60
Noul:   P(信息足够开始处理)       ──▶    actionableProbability = 0.60
Score:  0~3 优先级评分            ──▶    队列内排序（不参与门控）
```

- **模型负责给出概率**：温度校准之后，0.60 的语义是「这条弹幕的对象与诉求足以让助教开始处理」的置信度；
- **程序负责执行分流**：门槛是业务规则，不是模型属性——换模型、换判据、换场景，门槛都要重新量化；
- **人工兜底**：不满足门槛的消息进入「待确认」队列，由人工核对，不丢消息。

## 2. 为什么不能拍脑袋：三率三角

门槛调优本质是在三个比率之间找业务可接受的平衡：

| 比率 | 含义 | 过高/过低的影响 |
| --- | --- | --- |
| 完全自动正确率 | 判断正确且直接进对队列 | 越高自动化收益越大 |
| 进错队列率 | 类别判错但置信度/条件都过门槛 | 去错人，挫败感最强 |
| 漏处理/错放行率 | 该处理的被推到人工确认，或不该进的进了 | 人力成本 / 过度打扰 |

**课堂场景的业务偏好**：误进错误队列的挫败感 > 人工确认成本。所以本系统保留双门槛而非全自动化。

## 3. 实测扫描数据（v0.3 · 230 条，2026-10-26）

### 3.1 Noul 门槛扫描

| 门槛 | 覆盖率 | 区间判定一致率 | 通过区间实际可处理率 | 推到人工确认 |
| ---: | ---: | ---: | ---: | ---: |
| ≥ 0.50 | 74.8% | 89.6% | 91.9% | 25.2% |
| ≥ 0.55 | 74.3% | 89.1% | 91.8% | 25.7% |
| **≥ 0.60（当前）** | 72.2% | **90.4%** | 94.0% | 27.8% |
| ≥ 0.65（上一代） | 70.4% | 89.6% | 94.4% | 29.6% |
| ≥ 0.70 | 68.7% | 87.8% | 94.3% | 31.3% |
| ≥ 0.80 | 63.9% | 83.0% | 93.9% | 36.1% |
| ≥ 0.90 | 51.3% | 73.0% | 94.9% | 48.7% |

**两个结论**：

1. **0.60 已于 2026-10-26 业务采纳**：v0.3 分布下一致率最优（90.4%，覆盖 72.2%）——比上一代 0.65
   多 1.8pp 覆盖且一致率反而更高；该结论在 v0.2/v0.3 两代模型上均成立，且 v0.3 下更明确。
2. **0.80 再次被证伪**：v0.2 上一致率暴跌至 69.6%，v0.3 上修复至 83.0% 仍显著劣于 0.60–0.65 区间，
   且覆盖仅 63.9%——保守代价过大。

### 3.2 Choice 门槛扫描（top-1 概率）

| 门槛 | 覆盖率 | 通过区间分类准确率 |
| ---: | ---: | ---: |
| ≥ 0.50 | 85.2% | 81.6% |
| **≥ 0.60（当前）** | 70.0% | 86.3% |
| ≥ 0.70 | 59.6% | 88.3% |
| ≥ 0.80 | 43.9% | 91.1% |
| ≥ 0.90 | 27.4% | 93.7% |

0.60 仍是膝点：再往上每牺牲 ~10pp 覆盖只换 ~2–5pp 区间准确率。**结论：choice 0.60 维持不变。**

### 3.3 端到端分流模拟（进对队列 / 进错队列 / 漏到人工）

| choice | noul | 完全自动正确 | 进错队列 | 漏处理/错放行 | 人工确认兑底 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.60 | **0.60（当前）** | 48.7% | 6.1% | 11.3% | 33.9% |
| 0.60 | 0.80 | 45.2% | 5.7% | 15.2% | 33.9% |
| 0.70 | 0.60 | 45.2% | 4.8% | 15.7% | 34.3% |
| 0.50 | 0.50 | 53.0% | 10.9% | 6.5% | 29.6% |
| 0.70 | 0.80 | 42.2% | 4.3% | 19.1% | 34.3% |

当前组合（0.60/0.60，2026-10-26 采纳）：**48.7% 的消息全自动进对队列**，6.1% 进错队列，
11.3% 漏处理由待确认队列人工兑底——较 0.65 门槛（5.7%/11.7%）以 0.4pp 进错队列
换取 0.4pp 漏处理下降与 1.8pp 覆盖提升，且区间一致率反升 0.8pp（89.6%→90.4%）。
若追求更高自动化（0.50/0.50）可到 53.0%，但进错队列升至 10.9%——不建议。

## 5. 重算流程（模型迭代 / 判据变更 / 评估集扩充后）

```powershell
cd backend
# 1. 回放评估集（http 模式复用运行中的服务；--local 进程内加载）
.venv\Scripts\python.exe evals\replay_eval.py            # 产出 reports/eval-report.json
# 2. 阈值扫描（读 eval-report.json 的逐条概率）
.venv\Scripts\python.exe evals\threshold_scan.py         # 产出 reports/threshold-scan.md
# 3. （可选）双引擎对比
.venv\Scripts\python.exe evals\ab_runner.py              # 产出 reports/ab-report.md
```

同步三处：`src/config/criteria.ts`（门槛常量）→
`src/data/calibration.ts`（校准页数据快照）→ 本文档扫描表。

**重要**：判据（criteria 措辞）或温度变更会改变概率分布的含义，任何一者变化后
**必须**重跑回放再谈门槛，否则门槛数字失去语义。

## 6. 已知限制与下一步（v0.3）

1. **L3 已突破但未收敛**：22 条直播中断类真值样本命中 9 条（41%，零误报——9 条被判 L3 的真值全部为 3），
   12 条仍判 L2（不漏处理，仅排序略低）。v0.4/v0.5 两轮补种子实测：L3 命中最高 15/22（v0.4）
   但伴随 noul 回退（跷跷板效应，见 TRAINING.md 7.5 实战案例二），v0.3 综合最优维持默认——
   单点补强的边际收益已被三原语联动扰动抵消，下一步应走真实弹幕回流扩数据。
2. **低置信区（choice 0.2–0.4）仍过度自信**：实际 29.4% vs 平均置信 35.8%——
   缓解手段不变：该区间恰好被 0.60 门槛拦下进待确认，由人工兑底。
3. **chat 边界噪声**：夸赞/氛围/玩笑/打卡类闲聊被误判为听课反馈 10 条（v0.2 为 2 条）——
   v0.4/v0.5 注入 14 条 chat/feedback 边界对照后降至 7 条（仍高于 5 条目标），
   剩余为比较式夸赞/课程事务类难例；注意 v0.4 曾因把此类种子误标 actionable=false 教坏 noul
   （正确口径：chat 语义完整 = 信息充分 = true），教训见 TRAINING.md 7.5。
4. **评估集规模**：230 条覆盖五类与四级影响；招投标场景迁移（v1.0）时需按新判据重建评估集并重扫本表。
