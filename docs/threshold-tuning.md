# 阈值调优 · 双门槛量化依据

> 本文档回答一个问题：**「分类概率 ≥ 60% 且 处理条件概率 ≥ 65%」这两个门槛为什么是这两个数字，以及怎么在数据变化后重新校准它们。**
>
> 数据基线：230 条独立评估集（与训练集零重叠，含 22 条直播中断类）上的回放实测，
> 生成链路 `replay_eval.py → threshold_scan.py`，全部报告见 `backend/evals/reports/`。

## 1. 双门槛体系的职责边界

```
模型（Laya 微调 + 分桶温度校准）          程序（routing.ts 阈值分流）
────────────────────────────            ─────────────────────────────
Choice: 类别 + 全候选概率分布     ──▶    classifyProbability = 0.60
Noul:   P(信息足够开始处理)       ──▶    actionableProbability = 0.65
Score:  0~3 优先级评分            ──▶    队列内排序（不参与门控）
```

- **模型负责给出概率**：温度校准之后，0.65 的语义是「这条弹幕的对象与诉求足以让助教开始处理」的置信度；
- **程序负责执行分流**：门槛是业务规则，不是模型属性——换模型、换判据、换场景，门槛都要重新量化；
- **人工兜底**：不满足门槛的消息进入「待确认」队列，由人工核对，不丢消息。

## 2. 为什么不能拍脑袋：三率三角

门槛调优本质是在三个比率之间找业务可接受的平衡：

| 比率 | 含义 | 过高/过低的影响 |
| --- | --- | --- |
| 完全自动正确率 | 判断正确且直接进对队列 | 越高自动化收益越大 |
| 进错队列率 | 类别判错但置信度/条件都过门槛 | 去错人，挫败感最强 |
| 漏处理/错放行率 | 该处理的被推到人工确认，或不该进的进了 | 人力成本 / 过度打扰 |

**课堂场景的业务偏好**：误进错误队列的挫败感 > 人工确认成本。所以本系统保留双门槛而非全自动化。

## 3. 实测扫描数据（230 条，2026-10-25）

### 3.1 Noul 门槛扫描

| 门槛 | 覆盖率 | 区间判定一致率 | 通过区间实际可处理率 | 推到人工确认 |
| ---: | ---: | ---: | ---: | ---: |
| ≥ 0.50 | 73.0% | 87.0% | 91.1% | 27.0% |
| ≥ 0.55 | 71.3% | 87.0% | 92.1% | 28.7% |
| ≥ 0.60 | 70.4% | **87.0%** | 92.6% | 29.6% |
| **≥ 0.65（当前）** | 66.5% | 85.7% | 94.1% | 33.5% |
| ≥ 0.70 | 63.0% | 83.9% | 95.2% | 37.0% |
| ≥ 0.80 | 47.8% | 69.6% | 94.5% | 52.2% |
| ≥ 0.90 | 1.3% | 27.4% | 66.7% | 98.7% |

**两个结论**：

1. **0.80 被大样本证伪为过紧**：区间一致率从 87% 暴跌至 69.6%，一半消息被推向人工确认。
   这也回头验证了 v0.2 校准时 0.80 → 0.65 的调整方向正确。
2. **0.50–0.60 出现一致率平台（87.0%）**：其中 0.60 覆盖 70.4%（比 0.65 多 4pp）、
   通过区间质量 92.6%（比 0.65 低 1.5pp）。**数据支持 noul 门槛可从 0.65 下调至 0.60**——
   覆盖换质量的权衡点，是否采纳取决于业务对「错放行 1.5pp」的容忍度。

### 3.2 Choice 门槛扫描（top-1 概率）

| 门槛 | 覆盖率 | 通过区间分类准确率 |
| ---: | ---: | ---: |
| ≥ 0.50 | 80.9% | 82.3% |
| **≥ 0.60（当前）** | 68.7% | 83.5% |
| ≥ 0.70 | 55.7% | 88.3% |
| ≥ 0.80 | 42.6% | 90.8% |
| ≥ 0.90 | 26.5% | 93.4% |

0.60 是曲线的膝点附近：再往上每牺牲 ~13pp 覆盖只换 ~5pp 区间准确率。
**结论：choice 0.60 维持不变。**

### 3.3 端到端分流模拟（进对队列 / 进错队列 / 漏到人工）

| choice | noul | 完全自动正确 | 进错队列 | 漏处理/错放行 | 人工确认兜底 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0.60 | **0.65（当前）** | 47.4% | 6.1% | 13.5% | 33.0% |
| 0.60 | 0.80 | 37.8% | 4.3% | 23.9% | 33.9% |
| 0.70 | 0.65 | 43.5% | 3.9% | 17.8% | 34.8% |
| 0.50 | 0.50 | 53.0% | 9.1% | 7.8% | 30.0% |
| 0.70 | 0.80 | 35.2% | 3.5% | 26.5% | 34.8% |

当前组合：**47.4% 的消息全自动进对队列**，6.1% 进错队列（由队列内人工纠正），
13.5% 由待确认队列兜底，33% 原本就该人工看（chat 之外的确认类）。
若追求更高自动化（0.50/0.50）可到 53.0%，但进错队列升至 9.1%——不建议。

## 4. 推荐决策与当前状态

| 门槛 | 当前值 | 数据推荐 | 状态 |
| --- | --- | --- | --- |
| classifyProbability | 0.60 | 维持（膝点） | ✅ 已生效 |
| actionableProbability | 0.65 | 0.60 为覆盖-质量更优解（87% 平台内覆盖最高） | 待业务确认后调整 |

> 调整方法：改 [`src/config/criteria.ts`](../src/config/criteria.ts) 的
> `THRESHOLDS.actionableProbability`（页面文案全部动态读取该常量），
> 同步更新本文档与校准页数据模块 `src/data/calibration.ts` 的 `NOUL_THRESHOLD_OPTIONS`。

## 5. 重算流程（模型迭代 / 判据变更 / 评估集扩充后）

```powershell
cd backend
# 1. 回放评估集（http 模式复用运行中的服务；--local 进程内加载）
.venv\Scripts\python.exe evals\replay_eval.py            # 产出 reports/eval-report.json
# 2. 阈值扫描（读 eval-report.json 的逐条概率）
.venv\Scripts\python.exe evals\threshold_scan.py         # 产出 reports/threshold-scan.md
# 3. （可选）双引擎对比
.venv\Scripts\python.exe evals\ab_runner.py              # 产出 reports/ab-report.md
```

同步三处：`src/config/criteria.ts`（门槛常量）→
`src/data/calibration.ts`（校准页数据快照）→ 本文档扫描表。

**重要**：判据（criteria 措辞）或温度变更会改变概率分布的含义，任何一者变化后
**必须**重跑回放再谈门槛，否则门槛数字失去语义。

## 6. 已知限制与下一步

1. **等级 3（立即关注）系统性未命中**：22 条直播中断类真值样本 0 条被判中
   （19 条判 L2、分数 1.6~2.4）。原因指向训练集 L3 样本占比不足
   （322 条中仅 4 条种子）。**重训补强 L3 是当前最高优先的模型迭代项**；
   届时 Score 分桶温度（score:3-5 T=4.54）与本文档扫描需全部重算。
2. **低置信区（choice 0.2–0.4）过度自信**：实际正确率仅 28.6% vs 平均置信 36.5%——
   模型「犹豫时偏乐观」。缓解手段：该区间恰好被 0.60 门槛拦下进待确认，由人工兜底。
3. **评估集规模**：230 条覆盖五类与四级影响，但 chat/spam 的长尾变体仍有限；
   招投标场景迁移（v1.0）时需按新判据重新构建评估集。
